# Pi Personal Life Assistant

User-maintained lifestyle extension for pi 1.1.0 / Node 24.14.1 on Windows. Modules use Node built-ins, SQLite and pi's bundled TypeBox. No upstream vendor source is patched. `persona.md` supplies the full role; `extension.mjs` registers tools, consent dialogs and local commands; `store.mjs` owns versioned records; `finance.mjs` is deterministic; `network.mjs` fetches pinned public addresses; `documents.mjs` extracts allowlisted inbox documents with a fixed Python helper.

Entry: `../extensions/life-assistant.ts`. Launcher: `../deepseek-only.cjs`. User guide: `D:\PersonalAgent\使用说明.md`.

Run `node --test tests/*.test.mjs`. Optional `node tests/live-smoke.mjs` makes real DeepSeek requests using existing auth storage, but only fictional data in a temporary workspace. It does not print credentials, copy them into fixtures or populate the real database.

## Windows visual interface

### Startup and update recovery (2026-10-15)

The server snapshots its allowlisted interface files and reports a code revision at startup. A running backend never serves newly edited frontend modules against its old API or asset routes. The launcher compares the authenticated health revision to installed code before reusing the service. An outdated or disconnected service requires restart confirmation (`y` in the double-click launcher's terminal, or a pi `/app` confirmation). Cancellation leaves the old service untouched. Restart uses its authenticated shutdown endpoint and waits for exit; it does not kill unrelated processes. An unresponsive health check does not start a duplicate backend. `node gui/launcher.mjs --restart` explicitly confirms a needed restart; save other windows' inputs first.

The independent startup screen catches failed module imports, shows a slow-start warning after15seconds and offers retry or explicitly confirmed shutdown even if the main interface cannot load. Saved records are not changed by startup/retry. Check with `node --test tests/startup.test.mjs` and `node tests/startup-browser.mjs`; both use temporary fictional services and data. A full regression uses `npm test` and both training browser scripts below.

### Independent actual training and JSON import

In **身体与锻炼 → 记录真实训练**, use **＋ 直接记录训练** without generating a plan, or **导入训练记录（JSON）** to select a UTF-8 JSON file or paste JSON. Both paths preview all normalized records before an atomic local commit. No model/OCR service is used. Arbitrary app exports, screenshots and CSV are not currently supported; convert to the displayed `pi-training-v1` example first. Files are limited to60KB and1–50 daily records, each with1–30 exercises and1–50 sets per exercise, at most5000 expanded sets per batch. Records are grouped by date: combine multiple workouts on the same day. Existing actual records reject the entire batch instead of overwriting or counting twice. Use **更正实际训练** for corrections. Concurrent changes after preview also reject the batch.

Required fields are `date` (past/today, YYYY-MM-DD, Asia/Shanghai), `duration_minutes` (1–240) and `entries`. Each entry contains `name`, `focus` (`full_body/chest/back/legs/shoulders/arms/core`), optional `tracking_unit` (`reps` by default, or `seconds`), and `sets`. Sets contain either `reps` (1–100) or `seconds` (1–14400 for custom activities), optional `load_kg` (0–500) and optional `rir` (0–10). `source` and `notes` are optional; absent load/RIR remain unknown, not zero. Missing `energy`/`discomfort` remain `unknown`, not “normal” or “no pain”. File-supplied cloud consent is ignored; only the initially unchecked local checkbox authorizes sharing. Recovery is entered separately after import, not inferred.

```json
{"format":"pi-training-v1","records":[{"date":"2026-10-13","source":"训练笔记","duration_minutes":45,"entries":[{"name":"杠铃卧推","focus":"chest","sets":[{"reps":8,"load_kg":40},{"reps":6,"load_kg":40}]}]}]}
```

This example is fictional and is never prefilled or saved automatically. The existing schema4 envelope is retained: a standalone record uses `plan.mode: recorded`, empty planned exercises and `total_minutes: null`; this is metadata, not an invented prescription. An existing same-date unlogged plan retains its immutable snapshot while the confirmed actual record uses `independent: true`. Completion describes the actual training, not completion of prescribed exercises. Import does not change daily cumulative training metrics. Actual muscle labels feed recovery and planning; arbitrary exercise names are not guessed to match catalog exercises or used for automatic load progression. Revisions, deletion, export and existing cloud-read restrictions continue to apply.

### Split-based training and next-day recovery (0.7)

`training.mjs` asks for three-way push/pull/legs, five-way body-part, or custom split before planning. Split days suggest muscles, but the user can change the selection (for example, chest plus shoulders). Every selected muscle gets a distinct exercise or the planner rejects an insufficient time budget. Splits are rotation templates, not mandatory weekly frequency. Goal, experience, equipment, minutes, readiness and previous-day exertion shape warmup, main work, sets/reps or seconds, rest, RIR, technique cues and cautions. Only real logged sessions within 30 days can inform adjustments: soreness stays specific to actual trained muscles, while recent overall fatigue also affects different muscle days. Missing next-day recovery never implies readiness to increase load.

The existing schema 4 stores a structured, immutable split/multi-muscle plan snapshot, actual per-set log and independently confirmed next-day fatigue and soreness for each muscle actually trained within `training_sessions`; `training_versions` retains every revision. An incomplete workout must be marked partial, and correcting the actual trained muscles clears an incompatible recovery report before asking again. Older single-muscle plans remain readable. One structured plan per date prevents duplicating a multi-muscle day. Browser dashboard highlights completed workouts missing recovery feedback only after the workout day; there is no background reminder. Training/recovery edits require local preview/commit, reject stale revisions and do not auto-complete a workout or alter daily cumulative training metrics. Export `pi-life-v3` retains the nested recovery and all revisions. Existing general task plans remain intact.

Logs are local-only by default. A separate unchecked consent controls whether `life_training` and `life_workout` can read those logs in later model conversations. The one-off “给AI反馈” action previews precisely what will be placed into the chat draft, and the user must still press Send; it does not toggle long-term cloud sharing. Revoking consent removes historical model-query permission, not previously sent chat content or backups. API routes share existing loopback auth and CSRF protections. Unit, browser and privacy tests use fictional databases only.

### Embedded fitness tools (0.5)

The fitness view embeds local BMI calculation in `fitness.mjs`; the current browser workout flow uses `training.mjs` above. Height is a versioned `fitness/身高/fact` memory, strict numeric cm (50–250), not a fabricated daily measurement. BMI uses the latest actual weight, shows measurement sources and warns when older than30 days. No weight produces a missing-data state. Temporary calculator input never persists. China adult thresholds18.5/24/28 and WHO18.5/25/30 are selectable; classification uses unrounded BMI and is screening, not diagnosis.

The earlier general-task planner in `fitness.mjs` remains available for older workflows: reviewed `workout_save` creates a local-only planned task, not a structured training session or actual measurement. New browser workouts instead use reviewed `training_save` and `training_log`, with actual sets stored separately. Generating either template is read-only; daily cumulative minutes are recorded separately.

Authenticated `/api/fitness` and `/api/fitness/bmi` read local records without sending to DeepSeek. `/api/fitness/workout` uses local history and is read-only. Model tools `life_bmi` and `life_workout` use the same calculations: BMI only reads cloud-approved data or explicit parameters; workout progression only reads cloud-approved training logs. The browser form supports preserving long-term height separately from temporary calculation inputs. Tests cover boundaries, persistence, missing/stale data, derived-data privacy, safety/time budgets, duplicate protection and browser review flow.

Open `D:\PersonalAgent\打开生活助手.cmd`, or run `/app` / `/life-app` in a newly started pi terminal. `gui/launcher.mjs` starts or reuses a loopback-only HTTP service and opens an Edge app window. This is a browser-backed local interface, not a compiled Windows port of the Apple Silicon package. The vendor package is untouched; the personal launcher now explicitly loads `life-ui.ts` instead of its macOS `/app` extension.

`gui/rpc.mjs` maintains one pi RPC child and one active operation at a time, switches named sessions through the installed pi SessionManager/RPC, correctly decodes UTF8 JSONL with LF framing, streams deltas, and relays real human confirm/select/input/editor dialogs. Full snapshots on SSE reconnect restore state and pending approvals. Local dialogs timeout/cancel without approval. Daily edits use reviewed local proposals, not synthetic model messages; export/backup and terminal management remain available through local life commands. Chats and current terminal sessions are separate; approved memory/metrics/plans are shared.

`gui/server.mjs` binds only127.0.0.1 at a random port. Launch-token bootstrap, HttpOnly SameSite cookie, exact Host/Origin checks, and CSRF headers protect API access. CSP disables external assets, scripts and framing. Session and chart paths are allowlisted/canonicalized; no arbitrary RPC, shell or general file endpoint exists. Dashboard and SVG series are read locally. The local token in `data/life-ui-runtime.json` is not an API key but should still be protected. This is not isolation against other software running under the same Windows user.

Six Chinese views cover overview, streamed chat, actual body trends/history, personal records/history, plans/jobs and life skills. Drafts are retained per session in the current window's sessionStorage, including page refresh, not synced to other windows. Missing measurements are not filled, and gap>1day breaks lines. Exports still require confirmation; PNG/SVG/CSV/HTML downloads only serve generated chart filenames. Profile/plans show at most100 recent rows; metric history is paginated, and chart series max20000 records per metric. The service remains running when a window closes; use the sidebar power button to stop it.

`node tests/browser-smoke.mjs` uses installed Playwright/Edge and a real offline pi child against a temporary fictional database. `LIFE_PLAYWRIGHT_PATH` can specify an existing Playwright/core installation. Screenshots in `D:\PersonalAgent\examples\ui` are fictional, not personal records. Optional `node tests/gui-live-smoke.mjs` makes one small fictional real DeepSeek request and checks session recovery across a process restart. UI dependencies are only Node built-ins at runtime; browser automation is test-only.

### Workflow/data redesign

`catalog.mjs` is the single source of Chinese display labels, canonical storage units, validation bounds, daily aggregation semantics, and plan hierarchy kinds. English identifiers stay stable for old records and tools. `gui/public/forms.js` implements whole forms, review before commit, explicit unchecked cloud consent, inline errors, retained form values, and record-local edit/delete/history actions. Common body inputs are weight/waist; other metrics expand on demand. Chart export uses the currently selected metrics and date range without another selection wizard.

`local-actions.mjs` separates validate/read-only prepare from explicit commit. Pending proposals expire after5minutes, cannot be forged or re-used with changed payloads, and repeated commit requests return the same result in-process. Records are checked for concurrent corrections; duplicate measurements warn and conflict if another window added duplicates during confirmation. These routes require the same loopback authentication/Origin/CSRF protections as RPC. The model tool allowlist cannot access these endpoints or approve UI proposals. Local editing is independent of model generation.

SQLite `user_version=3` migrations create a pre-migration backup for populated databases, preserve existing measurements and correction dates, then add stable metric `record_id`, `revision`, `batch_id`, grouped entry batches, and a unique current version per logical record. Date/value/time/method corrections append revisions rather than deleting originals. `plan_versions` stores each future plan change; `parent_id` models goal→milestone→task, validates same domain/rank, prevents incomplete children beneath a completed parent, and requires reparenting before deleting a parent. Revoked cloud consent is removed from historical records too. Export `pi-life-v2` includes schema version, all measurement revisions, batches, plans and plan versions. Old plan edits predating this redesign cannot be reconstructed.

Dashboard latest readings are real measurements rather than daily averages. Task counts query all active/planned tasks, not a truncated list of goals/jobs/paused items. Chart daily readings average weight/waist/body fat/resting pulse; steps/sleep/training are daily totals and use the latest measurement for each day. Missing dates remain missing. UI history defaults to current measurements; optional old versions and export use the same date filter. Memory/plan screens still display the most recent100 rows, explicitly labeled; full data is available through export.

Core modules target this installation, including Python at `D:\Software\python311\python.exe` with PyMuPDF and matplotlib. Workspace/runtime paths live in `workspace.cjs`. Node SQLite is experimental; keep exports/backups and retest after Node/pi upgrades. The default workspace is `D:\PersonalAgent` and is intentionally not configurable by model parameters or inherited environment variables. The former F: workspace remains a pre-migration backup, not an active dependency.

Confirmations serialize to avoid overlapping dialogs. Database updates use immediate transactions and expected versions to detect concurrent memory/plan changes. Historical cloud permission is revoked when a memory correction becomes local-only. Read tools return only explicitly approved records. Local commands never send their input as model messages. Tool parameters entered in a chat are already cloud-visible before a save dialog; UI consent controls persistence and later reuse, not prior transmission.

Six allowlisted skills live in `skills/*/SKILL.md`. `resources_discover` registers only these paths even while default/shared discovery is disabled. Scenario bodies are selected before each prompt, and the model can read another through `life_skill`; `/skill:name` is supported. Tools never gain arbitrary file access because a skill was selected.

Metrics support time/method metadata, transactional batches, correction chains, date filtering and pagination. Existing schemas migrate without deleting values. `life_chart` reads the full current series (max20000 rows per panel, error rather than truncation), writes local PNG/SVG/HTML plus aggregated and raw CSV via a fixed Python renderer, and returns no numeric summary unless a separate UI confirmation approves it. `/metrics chart` can render local-only history without any model call and optionally open its offline page. A chart is an unencrypted data copy; metric deletion does not purge it. No external plotting service is contacted.

This is not an operating-system sandbox, data encryption system, scheduler, trading service or autonomous decision-maker. Prompt-injection resistance is policy plus constrained tools, not proof that advice cannot be influenced. Deletion cannot purge past transcripts, charts, backups or remote services. Metrics queries accept offset and up to500 rows; full export includes all rows. Optional `node tests/chart-preview.mjs` generates clearly fictional samples in the D: workspace's examples folder without populating the personal database.
